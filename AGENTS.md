## Verified Commands

**Frontend** (run from `src/frontend/`):

- **install**: `pnpm install --prefer-offline`
- **typecheck**: `pnpm typecheck`
- **lint fix**: `pnpm fix`
- **build**: `pnpm build`

**Backend** (run from `src/backend/`):

- **install**: `mops install`
- **typecheck**: `mops check --fix`
- **build**: `mops build`

**Backend and frontend integration** (run from root):

- **generate bindings**: `pnpm bindgen` This step is necessary to ensure the frontend can call the backend methods.
- **backend integration tests**: `scripts/test-backend.sh [section ...]` — PocketIC suite in `tests/backend` (keys, outcallAuth, verification, dispatch, tracking, stripe, openai, supportQueue, webhook, orders, pricing, load, scale, bigOrder, bigAudience, auditFixes, upgrade; `auditFixes` covers credit-pack grants, the $0.50 minimum, declared counts vs the canister-wide budget, a partly sent batch run and tracking across jobs; `bigOrder` stages a 12,000-recipient campaign in chunks and dispatches it as several print jobs, `bigAudience` saves, updates and reads back a 12,000-address saved audience and pages a campaign's recipients and CSV export; `pricing` bundles `src/frontend/src/lib/pricing.ts` and checks it against the canister's ledger, tier tables and campaign prices). Tests `src/backend/dist/backend.wasm` (rebuilt first when `mops build` is available).
- **end-to-end**: `scripts/test-e2e.sh` — the real frontend (built with `tests/backend/e2e/bridge.js` in place of the sign-in/actor package: a fixed Ed25519 identity, every actor call recorded on `window.__calls`) in Chromium against the real canister in PocketIC through its HTTP gateway: template → studio text/font/colour edits → reload (draft restored) → saved audience → Step 4 → create → print PDF → upload → test-mode payment → print hand-off (exact multipart, PDF pages and size, address-list XML, job form, submit) → tracking → campaign page. `E2E_LIVE=1` with `C2M_STAGE_USERNAME`/`C2M_STAGE_PASSWORD` and outbound access to `stage-rest.click2mail.com` sends the hand-off, verification and tracking to the print partner's real staging API instead. - **UI walk**: `scripts/test-ui.sh [route ...]` — builds the frontend with the e2e bridge (skipped with `UI_NO_BUILD=1`; `E2E_DIST` picks the dist) and walks it in Chromium against the real canister in PocketIC, seeded with a customer who is also the admin, a saved audience, a dispatched test-mode campaign and a draft: routes `home templates template-preview wizard-1 wizard-3-studio wizard-2 wizard-4 campaigns campaign-sent dashboard admin referral not-found stampy-open` × `UI_THEMES` (default `light,dark`) × `UI_VIEWPORTS` (default 360,390,768,1440). Overflow and banned copy fail the run; `UI_STRICT=1` also fails on contrast, light panels and theme mismatch.
- **pricing interpreter test**: `moc -r --package core <motoko-core>/src test/pricing.test.mo` — volume tiers, the cost floor, the member rule and `campaignCostCents` in `src/backend/lib/pricing.mo`; prints `pricing: all checks passed`.

## Learnings

- Product name is **EZmailout** (EZmailout.com). Printing and mailing run exclusively through the print partner's REST API (Click2Mail, `https://rest.click2mail.com/molpro`); the previous print vendor integration was removed. In the product, only the Admin page names it (see below).
- Provider names (Click2Mail, Stripe, OpenAI / DALL·E / GPT, Resend) appear in the product only on the Admin page, and only to the signed-in admin (`showProviders` in `AdminPage.tsx`: the "You are admin" banner above the integration keys, then the keys, webhook, public config and support inbox cards; the page header is the same for everyone, so it does not shift when admin status arrives); anyone else opening `/admin` — signed out or signed in — gets `NotFoundPage`, the same 404 as an unknown address, so the page does not reveal that it exists (a neutral spinner shows while the session and `getAdminKeys` load), and the header's Admin link is shown only when `useIsAdmin` says the caller is the admin or a controller. `getAdminKeys` tells a non-admin caller nothing but `callerIsAdmin = false`: no admin principal, environment, sandbox switch, webhook path or publishable key (`tests/backend` checks it). Stampy never points anyone to the Admin page: there is no `admin` nav key (frontend `NAV_CHIPS` or `Stampy.navKeys`/prompt), and account or settings questions go to the Dashboard. Everywhere else — storefront, wizard, studio, checkout ("Secure, encrypted checkout"), Stampy (its prompt forbids naming them), toasts, timeline, `index.html`, `project.json` — the wording is neutral ("payment processor", "AI copywriter", "AI backgrounds", "print"). A failed provider call returns `AdminLib.providerError(state, caller, detail, generic)`: the provider's own message only for the admin, because it names the provider and can quote part of a key (`Invalid API key provided: sk_live_****1234`); customers get the neutral `generic`. Text the print partner sends back (error descriptions, outcall failures naming its host, webhook scan text) goes through `Fulfilment.scrub` before it is stored or shown. `tests/backend` checks all of this (customer vs admin errors, scrubbed verification and webhook text). The OpenStreetMap attribution on the radius map stays (its licence requires it), as do "Sign in with Internet Identity" and the footer's caffeine.ai credit.
- White label: apart from the line above and the Admin page, nothing a customer or developer reads names the print partner. UI copy, toasts, backend error and timeline messages, the Stampy prompt, `index.html`, `project.json`, README and code comments say EZmailout, "print" or "print fulfilment" (Admin: "Print fulfilment" section, "Fulfilment API username/password/environment"). Identifiers are neutral too (migration `20261020_000000_FulfilmentNames` renamed the stable fields): `lib/fulfilment.mo` (module `Fulfilment`), `dispatchPrintJob`, `syncPrintTracking`, `verifyAddresses`, `printDocumentId`/`printAddressListId`/`printJobId`, `fulfilmentUsername`/`fulfilmentPassword`/`fulfilmentEnvironment` (`FulfilmentEnvironment`), `PublicConfig.fulfilmentConfigured`. The partner's name remains only where it is fixed elsewhere: its REST URLs, the legacy webhook path `/webhooks/click2mail` (still accepted beside `/webhooks/fulfilment`, `AdminLib.isWebhookPath`, because the partner may be configured to call it), and the immutable history in `migrations/` (file names and old field names). Never rename a past migration.
- Backend stable state is initialised only by the migration chain in `src/backend/migrations` (moc `--enhanced-migration`). Every new stable field needs a new dated migration whose `OldActor` equals the previous `NewActor`; module-level constants inside mixins must be `transient`.
- moc flags promote dot-notation (M0236) and redundant type args (M0223) to errors: call `caller.toText()`, `text.toLower()`, `r.toShared()` etc.; `Int.compare(a, b)` stays explicit.
- Public API stays bindgen-friendly: records with optional fields, payload-less variants, result records `{ ok; error }` — no `Result`, tuples (except the HTTP gateway types) or variants with payloads. The one exception is `_internet_identity_sign_in_finish`, whose type is fixed by the auth provider (see below).
- `src/frontend/src/backend.ts`, `backend.d.ts` and `declarations/` are generated from the compiled candid — never hand-edit.
- Pricing/credit constants live in `src/backend/lib/pricing.mo` + `lib/credits.mo` and are mirrored in `src/frontend/src/lib/pricing.ts` + `lib/credits.ts`; change both.
- Volume tiers: `PricingLib.volumeTiers` (`src/backend/lib/pricing.mo`) and `VOLUME_TIERS` (`lib/pricing.ts`) hold per-piece cents for under 1,000 / from 1,000 / 10,000 / 50,000 pieces (`tierMinimums`/`TIER_MINIMUMS`) on 4.25x6, 6x9, 6x11, letter and 11x8.5_brochure (the competitor's price less 1¢); every other row is flat at `retailPriceCents`, and a tiered row's `retailPriceCents` is its under-1,000 tier. A live member (`AccountLib.isSubscriptionLive`) is priced as at least 10,000 pieces. Every price covers the card fee at the processor's dearest card rate (`cardFeeBasisPoints` 440 + `cardFeeFixedCents` 30, i.e. 4.4% + 30¢: 2.9% for a US card plus 1.5% for an international one, so no card type can sell below cost; `CARD_FEE_BASIS_POINTS`/`CARD_FEE_FIXED_CENTS`) and still keeps 1¢ a piece over cost (`pieceCostCents`: `baseCostCents` + EDDM postage + class surcharge). Two prices: `pieceRateCents(row, qty, isMember, mailClass)` (both sides) is the per-piece rate price lists show — the tier plus postage and surcharge, never below `rateFloorCents(cost)` = ⌈(cost + 1) / 0.956⌉ (so 4.25x6 at 50k is 59¢, 6x11 from 10k 78¢, the brochure from 1,000 113¢, First-Class 6x11/brochure 103¢/139¢); `unitPriceFor(row, qty, isMember, mailClass)` / `getUnitPriceCents(variant, qty, isMember, mailClass)` is the order price createCampaign stores and Step 4 and the calculator quote — the rate, lifted to `orderFloorCents(cost, qty)` when a small order must also cover the fixed 30¢ (one 4.25x6 is 90¢, one EDDM 6.5x9 76¢; past a few pieces the lift is at most 1¢, e.g. brochures up to ~1,070 pieces). Tier tables, "from" prices, "members $X", the Stampy price list and the README use `pieceRateCents`; anything quoting a specific order uses the order price, and Step 4 / the calculator say "Small-order rate" when it is lifted. `calculateUnitPrice(row, qty, isMember)` is the order price at the row's own class. `test/pricing.test.mo` asserts that every row × class × quantity × membership covers the fee. `createCampaign` fixes the unit price and total on the record (`campaignCostCents` refuses an empty order or one over `maxOrderCents`); checkout charges the stored total and refuses a record whose total ≠ unit × count. Campaigns have no recipient limit (see "Campaigns of any size"), so every tier is reachable: "from" prices everywhere (Step 1, catalog bands, gallery, calculator, Stampy) use `startingPriceCents` (the last tier, `TOP_TIER_PIECES`, for tiered rows), and `tierSummary` / `volumeTierSteps` list each distinct tier (one the cost floor lifts to the previous price is left out). Orders must total at least `PricingLib.minOrderCents` / `MIN_ORDER_CENTS` (50¢, the payment processor's smallest card charge: `createCampaign` refuses a smaller order, checkout too unless sandbox mode is on, and Step 4 says so) and at most `PricingLib.maxOrderCents` ($999,999.99, the most one card payment can charge). Step 4 quotes by recipient count and membership (and waits for the account record before a signed-in launch, since the price depends on membership), shows the saving against the under-1,000 price and a member prompt for non-members. Once checkout is open, the invoice shows the canister's own price for the launched campaign (`campaignPrice` in the wizard store, from `createCampaign`'s `unitPriceCents`/`totalCents`, not persisted), and `StripeCheckout` labels Pay with the intent's `amountCents`; a launch reuses a draft only while `campaignPrice.totalCents` equals today's quote (a component-state copy was lost on navigation, so a customer who joined the membership saw the member price and was charged the old one), and an old draft is deleted (awaited) before a new one is created. EDDM® rows' ledger prices (`retailPriceCents`, 40–55¢) are print only: `calculateUnitPrice` / `getUnitPriceCents` add `postageCents(row)`, USPS EDDM Retail saturation postage (`PricingLib.eddmPostageCents` / `EDDM_POSTAGE_CENTS`, 26¢ from 12 July 2026; change both when USPS changes it), so every price shown or charged (Step 1, Step 4, the calculator, Stampy, "from" prices, `createCampaign`) is all-in and "every price includes printing and postage" holds for EDDM too; the rows' `note` names the postage and Step 4 lists it as included. Never show `retailPriceCents` as a price: go through `getUnitPriceCents`. First-Class on the formats priced for Marketing Mail whose volume prices cannot absorb the dearer postage (6x9, 6x11, 11x8.5_brochure: `PricingLib.firstClassSurcharged`) adds `firstClassSurchargeCents` / `FIRST_CLASS_SURCHARGE_CENTS` (24¢, USPS First-Class presort letters less Marketing Mail letters at mixed sort, July 2026 prices) a piece: `createCampaign` prices with `PricingLib.unitPriceFor(row, count, isMember, printSpec.mailClass)` (`calculateUnitPrice` is the default-class price), and the frontend passes the chosen `CatalogMailClass` as `getUnitPriceCents`' fourth argument (`classSurchargeCents`); Where a floor-priced tier binds, the dearer First-Class piece's own floor sits higher, so First-Class adds 24¢ to 26¢ a piece (6x11 from 10,000 and members 25¢, the brochure from 1,000 and members 26¢): Step 1's chip shows `firstClassAddLabel` ("+$0.24–$0.26/pc"), the selection summary lists the chosen class's own tiers (`tierSummary(variant, mailClass)` / `volumeTierSteps(variant, mailClass)`), Step 4 itemises this order's actual add (`pieceRateCents` First-Class − default class at this quantity and membership), and Stampy's prompt (`firstClassAdd()` in `lib/stampy.mo`) and quick answers quote the range. The flyer's flat price absorbs First-Class postage, so it has no surcharge. A draft keeps the price it was created at, so `createPaymentIntent` refuses one whose stored unit price is under what the same order costs today — `unitPriceFor(row, recipientCount, ownerIsMember, class)` with the owner's membership as it is now (it includes the order floor): a draft made before a postage, surcharge or fee change can never be paid below cost plus the card fee, and a member-priced draft cannot be paid once the 30-day pass has ended ("…the membership has since ended. Renew it … or re-run"). Member copy never says "from the first piece", "at any volume" or "regardless of volume": the small-order lift applies to members too, so it says "on small batches" / "at most the 10,000-piece rate" with the card-fee caveat, and Step 4's member prompt quotes the member order price for this order. AI credits come "with each 30-day membership", never "every month". Step 1's class chip on a format other than the selected one chooses that format in that class (the class travels through the "Start a new design?" dialog in `pendingFormat`), never changing the current selection's class. `CampaignSummary.mailClass` carries the stored class, and a re-run (`CampaignsPage`) sets it back with `setMailClass(wireMailClassToCatalog(…))`. Membership is a 30-day pass that never renews by itself (`subscriptionRenewsAt` is its end; a free month is used when the customer renews): copy says "Active until", "for 30 days", never "renews", "billed monthly" or "cancel any time". The README price table is generated from `PRICING_LEDGER` (all-in prices, distinct volume tiers); regenerate it when a price changes. Credit packs grant `Credits.packInfo(p).credits`, which already includes the bonus (`bonusCredits` is only the part shown as bonus). `test/pricing.test.mo` and `scripts/test-backend.sh pricing` check both sides.
- Campaigns of any size: a message carries at most 5,000 recipients (`maxRecipientsPerCall`, `MAX_RECIPIENTS_PER_CALL`; ingress is 2 MB), so `createCampaign` takes the first chunk and is priced for `recipientCount` (the whole list, never fewer than the chunk), and `addCampaignRecipients(campaignId, offset, recipients)` appends the rest in order (`RecipientStageResult { ok; error; stored; total }`; an empty chunk reports progress, a retried or overlapping chunk stores only what is new, nothing past `recipientCount`, nothing once paid). `createPaymentIntent` and `dispatchPrintJob` refuse until the stored list holds exactly `recipientCount`. Step 4 sends the first chunk with `createCampaign` (`INLINE_RECIPIENT_BYTES`, beside the canvas) and stages the rest (`recipientChunkEnd`, `RECIPIENT_CHUNK_BYTES`) with a progress bar, resuming from `stored` on a retry. Dispatch splits the stored list with `Fulfilment.addressListBatches` into address lists of at most `maxAddressListBytes` (1.8 MB: an outcall request is capped at 2 MB; sizes are counted with `addressXmlBytes`, never by building the XML, and the plan is made before the run's first `await` so it can never roll back a document upload), one print job each, planned once in the stable `printBatches` map (campaign id → `[PrintBatch]`, migration `20261025_000000_PrintBatches`); batch 0 mirrors the record's `printAddressListId`/`printJobId`, a retry resumes at the first batch not yet submitted (each probed like a single job), and the campaign is `#Submitted` only when every batch is; a run that stops after some batches went out stores `Fulfilment.partialFailure` ("Partly in production (k of n print jobs in production): …"), which `customerError` turns into "Partly sent to print …; send the campaign to print again to finish it" rather than "nothing has been printed". Tracking (`syncOne`) reads every job and aggregates all pieces' scans; a job's IMb tracking is read page by page (`Fulfilment.trackingPath(job, page)`: page 1 is the plain `/jobs/{id}/tracking?trackingType=IMB`, later pages add `&page=N`; `trackingPageCount` reads `totalPages`/`numberOfPages`/`totalNumberOfPages`/`pageCount`/`pages` from top-level JSON or XML, absent = one page; each reply up to `maxTrackingPageBytes`, 1.9 MB), and a job counts as answered only when every page was read: a failed page, a later page identical to page 1 (the parameter ignored) or more than `maxTrackingPages` (25) leaves it unanswered, never judged on part of its pieces. The page parameter and count names are not confirmed against the partner's reference (staging returns no tracking); a partner that does not page answers page 1 with everything, as before, and with several jobs moves the timeline only when every job's tracking answered (a stage from some jobs could mark the whole campaign delivered or returned, and it never moves back); the poll budgets 10 jobs per run (`maxPollJobsPerTick`), and webhooks match a later batch's job id through `printBatches`. The CSV uploader verifies 5,000 rows per call (`VERIFY_BATCH`, the canister's per-call limit), 5.5 s apart, and keeps the batches already verified for the same rows, so a list stopped by the hourly quota continues where it stopped. The wizard draft saves the audience under its own IndexedDB key (`<draft>:addresses`, written only when the list changes; the draft holds a `{ __ezAddresses: true }` marker, older drafts inline it), because re-serialising hundreds of thousands of recipients with every studio edit froze the editor. When a dispatch call gets no answer (a campaign of many jobs can outlast the browser's wait) Step 4 says the order is paid and to check Campaigns, not that it failed. Staging budgets: 1,000,000 unpaid recipients per identity (by declared `recipientCount`, so this is also the largest single campaign) and 1,500,000 *stored* unpaid recipients canister-wide (about 300 B each, up to ~900 B with long lines, so the heap stays inside the canister's memory); the canister-wide budget is charged as recipients are stored (`createCampaign`'s first chunk, every `addCampaignRecipients`) and `makeRoom` evicts idle unprotected drafts (never the one being staged) before refusing, so declaring a huge count without storing it blocks nobody; verification 250,000 addresses and 60 calls an hour per identity, 5 s apart. Saved audiences have no per-audience limit either (250,000 addresses per identity and 1,500,000 canister-wide, the same memory budget): `savePreset` / `updatePreset` take the first 5,000 addresses and `addPresetAddresses(presetId, offset, addresses)` appends the rest the same way (`useSavePreset` deletes a preset whose upload failed part-way, a thrown chunk call included; `useUpdatePreset` reports a partial save). Any stored list is read in pages of at most 2,000 (`AddressLib.page`, `RecipientPage { addresses; total }`): `getCampaignRecipientsPage`, `getPresetAddressesPage` and `exportCampaignRecipientsPage` (`CsvPage { csv; total }`, header on the first page, pages joined with newlines equal `exportCampaignRecipients`); the hooks read every page (`readAllPages`), because one reply is capped at a few MB. The whole-list `getCampaignRecipients`, `getPresetAddresses` and `exportCampaignRecipients` stay for compatibility; the frontend no longer calls them. `SavePresetDialog` lists the first 200 matching recipients and the filter finds the rest.
- Catalog: `src/frontend/src/lib/catalog.ts` lists the 14 print product families; `lib/pricing.ts` (`ProductSpec`, dollars) and `src/backend/lib/pricing.mo` (cents) hold the 29 authoritative rows and must be changed together. `documentClass` is the exact print product name and `widthInches`/`heightInches` follow that name's order. Legacy keys (`4x6`, `6x18_bifold`, `11x17_trifold`, `8.5x11_perforated`, `multi_page`) are aliased in `PricingLib.normalizeVariant` and `lib/pricing.ts` — never remove the aliases, older campaign records still carry them. `ProductType` keeps `#SelfMailer`/`#SnapPack` for old records; widening a variant used inside a stable `Map` needs an explicit migration (see `migrations/20260922_000000_Click2MailCatalog.mo`) because mutable fields are invariant.
- `ProductSpec.hasAddressBlock` drives the studio's USPS IMb clear zone: true only where the address is printed on the artwork the customer designs, false for envelope-inserted formats (letters, certified letter, priority, reply letter, notecards) where the print partner generates the address page or envelope.
- Mail class: products with several supported classes expose chips in the Step 1 accordion; the pick is stored in `wizard.selectedSpec.mailClass` and sent as the optional `CreateCampaignInput.mailClass`, which `PricingLib.printSpecFor` validates against the row's own classes (`PricingLib.rowMailClasses`, the same rule as the Step 1 chips: only a row that defaults to Marketing Mail may also go First-Class) before it reaches the print job. `StandardMarketing` in the catalog is the wire enum's `#MarketingMail`.
- Brand system (DESIGN.md): two themes of one tactile look. Light (default) keeps the original white EZmailout surfaces; dark is obsidian. The switch is `components/ui/theme-toggle.tsx` (`ThemeToggle`, variants `icon` (round 40 px, header from 390 px, `data-ocid="nav.theme.toggle"`, accessible name "Switch to dark mode" / "Switch to light mode"), `row` (phone menu, `nav.mobile.theme`) and `menu-item` (account dropdown, `nav.account.theme`, keeps the menu open), the last two a "Dark mode" switch (`role="switch"` / `menuitemcheckbox`, `aria-checked` on in the dark theme); callers pass the `data-ocid`). `lib/theme.ts` keeps the choice in localStorage `ezmailout_theme` ("light" | "dark", anything else = light), applies it as the `dark` class on <html> (which sets `color-scheme`), sets `<meta name="theme-color">` (#5c5ee8 light, #0a0b10 dark), follows other tabs, and exposes `useTheme()` (`theme`, `isDark`, `setTheme`, `toggleTheme`); `main.tsx` calls `initTheme()` before the first render (never an inline script: the CSP forbids it). Toasts (`ui/sonner.tsx`) follow it; there is no next-themes provider. The boot splash in index.html stays light (it paints before any script); `html.dark` repaints the root background. Tokens (index.css, oklch triplets; light → dark): page `--background` #F6F6F6 → #0A0B10, `--card` #FFFFFF → #12151E, `--card-raised` (`bg-card-raised`) #F9F9FB → #161A26, `--popover` (menus, dialogs, sheets) #FFFFFF → #131622, `--well` (`bg-well`, segmented tracks, sunken fields in dark) #ECEDF1 → #0D0F16, `--foreground` #01080A → #F4F5F9, `--muted-foreground` #56585B → #A1A6B4, `--muted`/`--secondary` #F5F5F5 / #F6F7F9 → #1C2030, `--accent` ice #CFF3FD → #1C2033 (never a CTA), `--border` #E5E5E5 → #262A38, `--input` (field borders, ≥ 3:1) #8A8D96 → #626881, `--ring` #5C5EE8 → #818CF8. `--primary` is the fill #5C5EE8 in both themes (white text 4.97:1); as text, `text-primary` reads `--primary-text` (#5C5EE8 → #A5A8FF), `text-destructive` `--destructive-text` (#C70A0D → #FF8A8A), `text-navy` `--navy-text` (#0E2B4F → #C9D8F0), `text-emerald-brand` `--emerald-ink` (#006645 → #3BE58F) and `text-amber-brand` `--amber-ink` (#92400E → #FFC24D), through `textColor` in tailwind.config.js, so one class passes AA as text and as a fill in both themes. Fills: `--emerald` #008058 and `--amber` (`bg-amber-brand`) #B45309 take white text (≥ 4.97:1), `--destructive` #E30205 → #DC2626 (white 4.9 / 4.8:1). Text on a pale primary tint (`bg-primary/10`–`/15`) uses `text-primary-ink` (#3F37BD → #C7C9FF, ≥ 6:1), never `text-primary-foreground` (white, for solid `bg-primary` only). On a solid `bg-primary` panel text is full `text-primary-foreground`, inner cards darken (`bg-black/10`), icons are `text-primary-foreground`. Delivery status moves only through `advanceStatus`, which applies `CampaignLib.deliveryMoveAllowed`: forward by `stageIndex` and only while `productionStatus` is `#Submitted`, so no webhook, poll or admin override can move an unpaid draft or a failed dispatch, and an outcome never goes back to the mail stream. `updateCampaignStatus` returns whether the campaign moved, and the Admin override offers only the stages StatusBadge's `deliveryMoveAllowed` (the frontend mirror) allows. A webhook for a campaign with no `printJobId` is refused; one for a job whose submission is unconfirmed is recorded as "not applied" without moving the timeline. AI endpoints keep a `settled` flag and refund the debit in `finally` if the reply's handling traps.

- Text extras (`lib/textStyle.ts`): a text block may carry `letterSpacing` (em), `lineHeight` (× size, default 1.2), `italic` and `rotation` (degrees, about the box centre) — `StudioTextBlock`. They are frontend-only: the editor (`textBlockStyle`, the transform on the element wrapper), the inspector (Spacing, Line height, italic, Turn°; weight 900), `textFit` (`FontSpec`; `widthOf` adds tracking, `bandHeight` uses the leading), `canvas.ts`'s refit and the rasterizer (tracking, leading, italic and rotation drawn on the alphabetic baseline) all read them through `textExtras`/`fontSpecOf`, and `canvasForStorage` strips them (`stripTextExtras`), so candid and the stable state are unchanged (no migration). Any measurement of a text block must go through `fontSpecOf(block)`, never `{ fontSize, fontWeight, fontFamily }` by hand. Preflight measures ink, not boxes: `textInkRect` for the safe area and `textLinesOverlap` (line rects, compared in their own frame when two blocks share a turn) for overlaps; the studio's safe-zone badge uses the same `outOfBoundsIds`. `canvasSignature` includes the extras, so italic or a turn ends a template's pristine state like any other edit. Text wraps through one function, `wrapText` (`lib/textFit.ts`: pre-wrap spaces kept, Chromium's in-word break opportunities via `hyphenSegments`/`breaksAfterDash`, measured from Chromium's own line breaker — after an ASCII hyphen before a letter, another hyphen ("e-mail-" / "-and") or opening punctuation, before a digit only when a letter or digit precedes the hyphen (never "-5", "$-5", "--5"); after a U+2010 hyphen or en dash before a letter, digit or opening punctuation; before an em dash unless an opening bracket or quote precedes it, and after one or an ellipsis before a letter, digit or opening punctuation — over-long words broken by character, the rest of the word then cut again as a line start, "pre" / "-19" / "90"), used by `countLines` and the rasterizer alike, so the PDF breaks lines where the editor does. Measurement matches what is drawn: `widthOf` uses the editor's font stack (`"Family", "Geist", sans-serif`, so a missing face or a character outside its range is measured in Geist) and letter-spaces natively (`ctx.letterSpacing`, which, like CSS, turns ligatures off; tracking added by hand measured "ff"/"fi" too narrow); spaces before a word that does not fit stay as a line of their own (an indented continuation); words are split by grapheme (`Intl.Segmenter`), never inside an emoji sequence, and the run that ends a split word is measured with the space after it (measuring with the next letter's kerning made more lines differ from Chromium, so it is not). A tab is one space everywhere (`shownText`: the editor, previews, the campaign page, measurement and print; `addTextBlock`/`updateTextBlock` store text without tabs), because the page laid tabs out at 8-space stops the print renderer did not reproduce. It compares widths as Chromium's line breaker does (rounded down to 1/64 px, and a run followed by a space measured with that space's kerning), the measuring context and the rasterizer kern like page text (`fontKerning = "normal"`: the canvas default kerned Playfair up to 0.5 px wider), and the rasterizer wraps at design size (`textWidth`), where the editor lays text out, then draws at print size. Checked against Chromium's own layout over Geist, Barlow, Playfair, Pacifico and Bebas, with and without tracking: about 0.7% of layouts still differ, all of them words wider than their box split letter by letter (long URLs in very narrow boxes). Step 4's preflight also fails on text or a QR code in the back's USPS zone (warns on artwork there; `data-ez-bleed`/`data-ez-zone` art is exempt) and on a static QR code with nothing to open; the rasterizer gives a bare domain in a static code `https://`.

  - Webhooks: a delivery outcome (Delivered/Undeliverable/Returned) from a webhook settles only a one-piece, one-job campaign; for anything larger the event is recorded and tracking (`aggregateStage` over every piece and job) decides, because a settled campaign stops being tracked.
  - Print-file uploads: chunk 0, or any chunk after a complete file, starts a new `DocumentUpload` (`uploadDocumentChunk`); reusing the complete upload let a re-upload's new chunk 0 plus the old chunk 1 count as a complete, payable file.
  - Return address: `createCampaign` requires one that passes `Inputs.returnAddressError` (name, street, city, 2-letter state, 5-digit ZIP or ZIP+4, the review form's `validateReturnAddress` rules), and `createPaymentIntent` refuses a draft without one: dispatch needs it and a paid order's cannot change. Step 4's preflight fails while the return-address form has unsaved edits (`returnAddressUnsaved` in the wizard store, not persisted).
  - Print environment: `printEnvironments` (campaign id → `FulfilmentEnvironment`, migration `20261026_000000_PrintEnvironments`) is recorded by the dispatch that first reaches the print partner (re-recorded while the partner holds nothing, `partnerHoldsAny`), and `environmentFor` uses it for every later step and tracking lookup, so switching the admin's setting cannot send a job's tracking or a retried batch to the other environment.
  - `createPaymentIntent` re-checks that a campaign order's draft still exists and is still unpaid after the payment processor answers (eviction, expiry, or a payment from another tab can land during the call) and hands out no checkout otherwise; it also refuses an intent id that already has a payment record (the create call is answered by one node, so a reused id could reset a settled payment and grant it twice). `firstPaymentAt` is set only by a payment that settles its campaign (not a duplicate or orphan).
